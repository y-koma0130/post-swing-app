# 認証とセキュリティの方針

## 決定事項（2026-11-14）

- 認証は **Better Auth** を使い、ユーザー・セッションのデータは**自分の D1** に持つ
- **パスワードは扱わない。** ログインは LINE とメールのワンタイムコードだけ
- **カード番号は扱わない。** 決済情報は Stripe が持つ
- 管理画面は Better Auth ではなく **Cloudflare Access** で守る

### Better Auth を選んだ理由

- LINE ログイン、メールのワンタイムコード、トークン認証、Expo 連携が標準でそろう（v1.7.14 を使用）
- データが自分の D1 にあるので、売却時に Cloudflare アカウント1つで引き継げる
- 利用者が増えても費用がかからない
- Next.js の内部の仕組みに依存しないので、vinext で動かしやすい

### 外部の認証サービスにしなかった理由

外部に出しても、流出して困るデータの大半（スイング動画、チャット、添削の内容）は自分で持つしかない。パスワードとカード番号は最初から持たないので、外部に出して減るのは名前・メールアドレス・LINE のIDくらい。個人情報保護法上も、預け先を監督する責任と、流出したときに報告する義務はこちらに残る。

| 案 | 見送った理由 |
|---|---|
| Clerk | vinext で動くか未確認。ユーザー情報が外部に置かれる。利用者数に応じて費用がかかる |
| Auth.js | 開発チームが Better Auth に合流し、今後の発展が見込みにくい |
| Supabase Auth・Firebase Auth | LINE ログインに追加の設定や有料プランが必要。D1 とは別のサービスに依存する |
| 自作（Arctic など） | セッション管理やメールログインを自分で書く手間が、検証段階に合わない |

## ログインの方法

| 利用者 | 方法 | 段階 |
|---|---|---|
| 生徒 | LINE ログイン | 1〜（段階1のトークンは作らず、最初から LINE にした。2026-11-14） |
| 生徒・コーチ（開発中だけ） | メールの6桁コード。コードはメールで送らずログに出す | ローカルのみ |
| コーチ | メールの6桁コード（Better Auth の `email-otp`）。本番は招待済みのメールアドレスだけ | 1〜 |
| コーチ | Google ログイン（要望があれば） | 2〜 |
| 管理者（自分） | Cloudflare Access | 1〜 |

### LINE ログインの設定

- LINE ログインのチャネルと、通知用の Messaging API のチャネルは、LINE Developers の**同じプロバイダーの下**に作る。別にすると同じ人でもユーザーIDが変わり、ログインした生徒に通知を送れない
- ログイン時に公式アカウントの友だち追加を促す（`bot_prompt=aggressive`）。友だちでない人には通知を送れない
- スコープは `openid profile` だけにする。メールアドレスは取得しない

### コーチのログインをメールのコードにする理由

インスタや LINE のアプリ内ブラウザから開くと、メールのリンクが別のブラウザで開き、ログインが途切れやすい。6桁のコードなら同じ画面に入力できる。

- コードの有効期限は10分、5回間違えたら無効にする
- コードの送信は、同じIPから1分に1回まで（Better Auth の回数制限は IP ごとに数える。Worker はメモリを共有しないので、記録は D1 の `rate_limit` に置く）。開発中は止めている
- メールは Cloudflare Email Service で送る。届きにくければ Resend に切り替える

### LINE のユーザーとメールアドレス

Better Auth はユーザーにメールアドレスを必須とする。LINE ではメールを取らないので、`line_<LINEのユーザーID>@users.swingpost.invalid` という届かない仮のアドレスを入れる（`.invalid` は送信されないドメイン）。

## セッション

- Cookie は `HttpOnly`・`Secure`・`SameSite=Lax`
- セッションは D1 に保存し、サーバー側で無効にできるようにする（ログアウト、端末の紛失時）
- `cookieCache` は短め（5分程度）にして、D1 への問い合わせを減らす
- 将来のアプリは Better Auth のトークン認証（`bearer`）や Expo 連携で、同じセッションの仕組みを使う

## コードの置き場所と流れ

```
src/server/
├── auth/                    Better Auth の設定（D1・Drizzle に接続）
│   ├── auth.ts              betterAuth({...}) のインスタンス
│   └── getActor.ts          リクエストから「誰が操作しているか」を取り出す
└── features/<feature>/
    ├── presentation/        getActor() でログインを確認し、actor をユースケースに渡す
    └── application/         actor（userId と役割）を引数で受け取る。Cookie やトークンは知らない
```

- Better Auth の API は Route Handler（`src/app/api/auth/[...all]/route.ts`）1つで受ける
- domain・application は Better Auth に依存しない。Web の Cookie でもアプリのトークンでも、同じユースケースを使える
- ユーザーは1つの表（Better Auth の `user`）にまとめ、コーチのプロフィールを1対1で別の表に持つ。コーチが他のコーチの生徒になる場合にも対応できる

## セキュリティ対策

流出の多くは、データベースそのものが破られるより、周辺の設定やアカウントの管理から起きる。次を段階1から守る。

### 持たない・すぐ消す

| 対象 | 方針 |
|---|---|
| パスワード | 持たない |
| カード番号 | 持たない（Stripe） |
| LINE のメールアドレス | 取得しない |
| LINE のアクセストークン | 暗号化して保存する（Better Auth の `encryptOAuthTokens`） |
| 生徒の動画 | スレッド終了から一定期間後に自動で削除する（期間は未定） |
| ログ | 名前・メール・本文・トークンを出さない。IDだけを出す |

### 見せる範囲を絞る

- 「このスレッドの持ち主（担当コーチ・本人の生徒）か」の確認を**ユースケースで必ず行い**、テストを書く
- 他人のIDでアクセスされたら、「権限がない」ではなく「存在しない」と返す（IDが存在するかどうかを推測させない）
- R2 は非公開のまま使う。動画や画像は、数分で期限が切れる署名付きURLでだけ見せる
- アップロード用の署名付きURLは、保存先・ファイルの種類・サイズの上限を指定して発行する

### アカウントと秘密情報

- Cloudflare・GitHub・Stripe・LINE Developers は、パスキーか2段階認証を必須にする
- 秘密情報は Workers Secrets だけに置く。コード・リポジトリ・ログに書かない
- Cloudflare の API トークンは、用途ごとに必要な権限だけを付ける
- 管理画面（`/admin`）は Cloudflare Access の奥に置く

### アプリの実装

- SQL は Drizzle で組み立て、文字列をつなげて作らない
- 外から来る値は、すべて zod で検証してから使う
- Server Actions でも、ログインと権限を毎回確認する（画面に出ていない操作も直接呼ばれうる）
- フォームの送信やコードの送信には回数制限をかける（Cloudflare の Rate Limiting、申し込みフォームには Turnstile）

### 備え

- D1 は Time Travel（過去の時点に戻す機能）で復旧できるようにしておく
- 流出のおそれがあるときは、個人情報保護委員会への報告と本人への通知が必要になる（速報は発覚から3〜5日程度、確報は30日以内が目安）。手順は段階2までに決める
